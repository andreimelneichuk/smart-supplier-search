# Поиск поставщиков продуктов питания

Сервис для закупщика: найти производителей нужного продукта рядом с нужным городом, собрать по ним ключевую информацию, сравнить и решить, кому писать первым.

Тестовое задание на позицию **AI Generalist / AI Automation Specialist** (часть 2).

**Демо:** https://smart-supplier-search-6o5krctpkuhqe28gnyqrti.streamlit.app/ · **Репозиторий:** https://github.com/andreimelneichuk/smart-supplier-search

---

## Как этим пользоваться

1. Пишете запрос обычными словами: «сыр моцарелла Казань», «мясо индейки», «мёд липовый в Питере». Город можно указать в запросе или выбрать в фильтре.
2. Получаете список производителей: сначала те, у кого это основной продукт, и те, кто ближе к вам. У каждого видно город, расстояние, контакты, сайт и ссылку на источник. Кроме «лучшего совпадения» список можно отсортировать: «ближе к городу», «надёжнее» (полнота карточки: телефон, почта, ассортимент, описание) или «шире ассортимент». В этих сортировках сначала идут компании, у которых искомый товар точно есть. Если в городе таких нет, сервис пишет об этом прямо.
3. Открываете «Паспорт» поставщика. LLM разбирает полный текст карточки и собирает в одно место минимальный заказ, цену, фасовку, оплату, сертификаты (ГОСТ, ХАССП, «Меркурий», «Честный знак»), условия доставки, плюсы, риски и вопросы для первого звонка.
4. Добавляете 2–4 кандидатов в «Сравнение» (вручную или кнопкой «отобрать через AI»). LLM сравнивает их, советует, с кем связаться первым, кто будет запасным вариантом, и пишет черновик первого сообщения.
5. Ведёте статусы и заметки по поставщикам («Отправлен запрос КП», «Ждём прайс», …) с историей и авторами. Заметки разделены по организациям.

## Как это работает

```
запрос ─► разбор: продукт, уточнения, город
        ─► кандидаты: BM25 по полям, плюс поиск на productcenter.ru по фразе
        ─► итоговый балл = 0.40·релевантность + 0.40·близость + 0.10·полнота карточки + 0.10·размер
        ─► карточки, паспорт по запросу (LLM, кэш в SQLite), сравнение и CRM
```

- **Релевантность.** Лемматизация `pymorphy3`, поиск по нескольким полям с разными весами (специализация, название, категория, описание). Отдельно различаются основной продукт и побочный («пельмени с курицей» не считаются поставщиком курицы), непищевые товары (корм, приправа, упаковка) и родительские категории (птицефабрика при запросе «индейка» получает частичный балл).
- **Гео.** Город берётся из запроса или фильтра, координаты — из офлайн-справочника на 1100 городов, а если города там нет — из Nominatim с кэшем. Близость считается так: `exp(-(d - d_min) / 400 км)`, то есть ближайший поставщик получает 1.0. Пока товар подходит плохо, близость влияет на балл слабо, чтобы соседняя, но нерелевантная компания не обгоняла нужную.
- **Данные.** Около 5000 производителей с productcenter.ru и agroserver.ru (`productcenter_parser.py`, `agroserver_parser.py`, `expand_catalog.py`). Для ~1300 из них LLM заранее разметил товары и признаки (`enrich_catalog.py`). Контакты и свежие компании подтягиваются с сайта прямо во время поиска (`live.py`). Если сайт начинает отвечать ошибками, на 5 минут включается пауза, и сервис работает только на своей базе.
- **Проверка ответов LLM.** Промпт запрещает додумывать, но модель может его нарушить, поэтому её ответ проверяется кодом (`advisor.py`: `unsupported`, `ground`, `check_advice`):
  - число (цена, партия, срок) или документ (ГОСТ, ТУ, ХАССП, «Меркурий», ЕАС…), которых нет в тексте карточки, заменяется на «не указано», а из совета вырезается предложение с ним;
  - компании в совете должны быть из выбранных и разными;
  - есть ли у компании искомый товар, сервис проверяет сам по карточке и показывает отдельной пометкой, а не верит модели;
  - кто ближе, считается заранее и передаётся модели готовым местом по близости.

  Остаётся риск неверных формулировок без цифр («надёжный партнёр»), поэтому совет подаётся как черновик для закупщика.
- **Паспорт по запросу.** Заранее выкачивать и разбирать LLM всё подряд дорого, да и сайт за это блокирует. Поэтому подробное досье собирается только для поставщиков, которых открыли, и сохраняется в кэш.

## Почему такой формат

- **Streamlit + SQLite.** Работающий прототип в одном процессе, без отдельного фронтенда и сервера БД. Он разворачивается одной кнопкой, и его легко показать. Для боевой версии логика (`ranking.py`, `search.py`, `advisor.py`) не завязана на интерфейс и выносится в API как есть.
- **Поиск без нейросетей, LLM только там, где нужен текст.** BM25 по полям работает бесплатно и офлайн, без загрузки моделей. LLM (Groq, OpenAI-совместимый API) вызывается только для паспорта, сравнения и черновика письма, и его ответы кэшируются. Без ключа API поиск, карточки и CRM работают, недоступны только AI-функции.

## Ограничения и что дальше

- Цена и минимальный заказ есть только там, где поставщик сам их указал. В остальных случаях это «по запросу», и сервис подсказывает, что спросить.
- База — снимок открытых каталогов. Дальше: регулярное обновление, больше источников (сайты производителей, Честный знак, ЕГРЮЛ для проверки юрлица), авторизация пользователей вместо выбора организации в списке.

## Качество поиска

`parser/eval_search.py` сравнивает варианты поиска на 21 запросе с ручной разметкой (`parser/eval_labels.json`):

| вариант | P@10 | nDCG@10 |
|---|---|---|
| только эмбеддинги | 0.34 | 0.58 |
| BM25 по полям | 0.66 | 0.90 |
| BM25 + эмбеддинги (RRF) | 0.56 | 0.79 |
| + cross-encoder | 0.64 | 0.96 |
| **весь пайплайн сервиса** (`ranking.rank`: роли слов, синонимы, отсев непищевого и производных, склейка дублей) | **0.76** | **0.96** |

P@10 не может быть выше доли релевантных: по узким запросам («мясо индейки», «яйцо перепелиное») в базе всего 2–5 подходящих производителей. Поэтому главная метрика — nDCG. Выдача сервиса доразмечена вручную по тем же правилам: релевантен производитель именно этого товара.

Что дала доводка поиска:
- синонимы: «тушенка» → «тушёное мясо», «мясные консервы» (P@10 с 0.0 до 1.0), «креветки» → «морепродукты»;
- оборудование и корма «для птицы» больше не получают балл родительской категории по запросу «курица».

Слабые места: «колбаса копчёная», «рыба солёная» — способ обработки в карточках обычно не указан, поэтому находятся все колбасные и рыбные производители. «Креветки замороженные», «хлеб ржаной» — профильных производителей в базе мало.

### Отложенный набор

`parser/eval_holdout.py` проверяет 14 запросов, которые не использовались ни для подбора весов, ни для синонимов (`parser/eval_holdout.json`):

| вариант | P@10 | nDCG@10 |
|---|---|---|
| BM25 по полям | 0.94 | 0.99 |
| + cross-encoder | 0.92 | 1.00 |
| **весь пайплайн сервиса** | **0.94** | **1.00** |

В облачной версии сервиса cross-encoder отключён: модели не помещались в лимит памяти Streamlit Cloud, а на этом наборе прироста качества он не дал. Сервис ранжирует по варианту «BM25 по полям» с отбором и весами из раздела выше.

Ограничения честно: разметку делал один человек, глядя на подкатегорию и основные товары карточек; пул кандидатов — подстрока запроса в тех же полях, поэтому компании без этого слова в карточке в разметку не попали и метрика их не видит. Запросы простые (творог, гречка, квас), у них много явных производителей, поэтому цифры выше, чем на узких запросах из основного набора. Это проверка, что сервис не переподогнан, но не замер качества на произвольных запросах.

```bash
cd parser && python eval_holdout.py        # отложенный набор
cd parser && python eval_search.py score   # основной набор, пересчитать
cd parser && python eval_search.py pool    # кандидаты для доразметки
```

### Какие поля есть в базе

Доли карточек из `parser/dbstats.py` (снимок базы, 4857 производителей):

| поле | доля карточек |
|---|---|
| город | 100% |
| описание (от 100 знаков) | 96% |
| ассортимент (число товаров) | 96% |
| основные товары (LLM-разметка) | 27% |
| телефон | 3% |
| e-mail | 4% |
| контакты проверены с сайта | 4% |
| упомянута цена в тексте карточки | 0% |
| упомянут минимальный заказ в тексте карточки | 0% |

Телефон и почта в снимке почти отсутствуют: их подтягивает `live.py` с сайта при поиске, поэтому в карточке помечено, проверялись ли контакты и когда. Цена и минимальный заказ в снимке не указаны ни у одного поставщика: паспорт собирает их из полного текста страницы при открытии, и без этого сервис честно пишет «по запросу».

```bash
cd parser && python dbstats.py    # пересчитать таблицу и дату базы
```

## Тесты

```bash
cd parser && python -m pytest      # разбор запроса, близость, сортировки, дедупликация, RRF, эталонные запросы на базе
```

Тесты в `parser/tests/`: `test_ranking.py` (город из запроса, расстояние до ближайшего поставщика, сортировки, склейка дублей), `test_geo.py` (гаверсинус, справочник городов), `test_search.py` (лексический поиск, RRF, эталонные запросы на текущей базе).

## Запуск локально

```bash
git clone https://github.com/andreimelneichuk/smart-supplier-search.git
cd smart-supplier-search
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env        # впишите ключ Groq или OpenAI, чтобы включить AI-функции
streamlit run parser/app.py
```

Готовая база (`parser/suppliers.db`) и кэш эмбеддингов лежат в репозитории, поэтому сервис работает сразу после клона. Нейросетевые модели для поиска не нужны и ничего не скачивается.

## Деплой на Streamlit Community Cloud

1. share.streamlit.io → New app → этот репозиторий, ветка `main`, файл `parser/app.py`.
2. Advanced settings → Secrets:
   ```toml
   OPENAI_API_KEY = "gsk_..."
   OPENAI_BASE_URL = "https://api.groq.com/openai/v1"
   OPENAI_MODEL = "qwen/qwen3.8-27b"
   ```
   Streamlit сам передаёт эти значения в переменные окружения.

## Структура

```text
parser/
  app.py                 интерфейс (Streamlit)
  ranking.py             разбор запроса и итоговый балл
  search.py, bm25.py     лексический и векторный поиск, RRF
  cross_encoder.py       переранжирование (ONNX); в облачной версии не используется
  llm_rerank.py          опциональное переранжирование через LLM
  advisor.py             паспорт поставщика, сравнение, черновик письма
  geo.py, data/city.csv  координаты и расстояния
  live.py                подгрузка с productcenter.ru во время поиска
  db.py                  SQLite: поставщики, кэши, CRM
  *_parser.py, expand_catalog.py, enrich_catalog.py   сбор и обогащение базы
  eval_search.py, eval_labels.json                    оценка качества поиска
  eval_holdout.py, eval_holdout.json                  отложенный набор запросов (не для настройки)
  dbstats.py                                           доли полей в базе и дата снимка
  tests/                                              pytest: ranking, geo, search
```
